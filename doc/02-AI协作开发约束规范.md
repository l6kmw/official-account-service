# AI 协作开发约束规范

> 这份文档不是"最佳实践建议"，是**硬性规则**。所有 AI 编码任务在开始前必须读取本文档作为上下文；提交代码前必须对照第 5 节自查清单逐项确认。

## 0. 为什么需要这份文档（第一性原理）

AI 写代码和人写代码的失败模式不一样。人会因为"懒"而抄近路，AI 会因为**局部最优**而抄近路——它会在当前这一个任务范围内把代码写"对"，但不知道、也不关心这段代码放到整个系统里是否破坏了架构边界。具体表现为几类典型失败：

1. **静默吞错误**：`if err != nil { return nil }`，编译能过、测试能过（如果没写覆盖这个分支的测试），但线上出问题时无迹可寻
2. **重复造轮子**：因为 AI 在单次任务里看不到全局，容易在多个地方重复实现同一段逻辑（比如到处手写 tenant 过滤条件）
3. **边界渗透**：为了让某个 handler"快速跑通"，直接在 HTTP 层写 SQL、在 domain 层 import 了 Gin 的类型
4. **过度自信的完成声明**：AI 倾向于说"已完成"，但没有对应测试、没有验证边界情况

这份文档的作用就是把"人类工程师凭经验会注意的东西"显式化，变成 AI 可以对照检查的规则表。

## 1. 分层依赖铁律

```
interfaces (http / wechat_callback)
        ↓
   application
        ↓
     domain   ←──  infra (实现 domain 定义的接口)
```

| 层 | 可以 import | 禁止 import |
|---|---|---|
| domain | 标准库、其他 domain 子包 | Gin、ent、Redis、asynq 等任何框架/基础设施包 |
| application | domain | Gin、ent 等具体实现包（只能依赖 domain 定义的接口） |
| infra | domain（实现其接口）、具体框架 | application、interfaces |
| interfaces | application | infra 的具体实现（应通过 application 暴露的接口访问） |

**违反此规则视为严重缺陷，必须打回重写，不接受"能跑就行"。**

判断方法（AI 自查时用）：打开一个文件，看它的 import 列表，凡是出现"层级表中禁止 import 的包"，直接判定违规。

## 2. 强制规则（MUST）

1. 每个导出（大写开头）的函数/方法/类型必须有符合 Go 规范的注释（以名称开头）
2. 每个 `error` 返回前必须用 `fmt.Errorf("...: %w", err)` 附带上下文再返回，禁止裸传
3. 禁止用 `panic`/`recover` 处理业务错误（可以在 `main.go` 或中间件层做兜底 recover，防止进程崩溃，但业务逻辑内部一律用 error 返回）
4. 所有涉及 `tenant_id` 的数据访问，必须通过 repository 层强制要求 `tenantID` 参数的方法进行，不允许在 service/handler 里裸写查询绕过
5. 所有对微信 API 的 HTTP 调用必须设置超时（建议 5~10s），并接入统一的重试（幂等接口）和熔断策略，不允许裸用 `http.Get`
6. 所有写操作（尤其是回调触发的写操作）必须考虑幂等，重复调用不应产生重复副作用
7. 涉及密钥/token 的字段（`*secret*`、`*token*`、`*refresh*` 等命名）一律不允许出现在日志、`error` message、或任何返回给前端的字段里；确需记录，只能记录脱敏后的摘要（如前 4 位 + 掩码）
8. 每个 PR 对应的核心逻辑必须包含单元测试；涉及并发/幂等的逻辑必须有并发场景测试
9. 所有 HTTP 入参必须经过 `validator` 校验后才能进入业务逻辑
10. 新增或修改数据库 schema 必须配套写迁移文件，不允许手动改库

---

## 3. 禁止清单（MUST NOT）

1. 禁止使用包级全局可变变量存储运行时状态（配置对象等应通过 wire 注入，不允许 `var globalDB *sql.DB` 这种写法）
2. 禁止在 `interfaces/http` 的 handler 函数里出现业务判断逻辑（超过"参数解析 → 调用 application → 序列化返回"这三步的都算业务逻辑，必须下沉到 application 层）
3. 单个函数超过约 60 行、单个文件超过约 400 行，视为需要拆分的信号，不允许无理由地继续堆砌
4. 禁止用 `interface{}`/`any` 作为参数或返回值来"偷懒"绕过类型系统写"万能函数"
5. 禁止直接使用 `fmt.Println`/`log.Println` 打日志，必须走统一的 `zap` logger
6. 禁止把 `component_appid`、`appsecret`、任何密钥硬编码在代码里（哪怕是"临时测试"），一律走配置/环境变量
7. 禁止一个 commit/PR 同时改动"跨越两个以上分层"的大范围代码（比如同一个 PR 既改 domain 接口定义又改 3 个 infra 实现又改 2 个 handler），这类改动必须拆成多个可独立审查的小 PR
8. 禁止在没有幂等保证的情况下，让微信回调的重试直接触发业务副作用（发消息、扣计数等）

## 4. 任务拆解规范（用于 orchestrator 向 AI 分发任务）

给 AI 的每一个开发任务，描述时必须包含以下字段，缺一不可：

```text
【任务名】
【所属分层】domain / application / infra / interfaces 中的哪一层
【输入契约】这个任务要实现的函数/接口，明确的输入类型和约束
【输出契约】明确的返回类型、error 情况的定义
【允许修改的文件范围】显式列出文件路径，禁止超出此范围改动
【禁止修改的文件范围】显式列出不允许碰的文件（比如已冻结的 domain 接口定义）
【验收标准】可验证的具体条件（如"并发 100 次调用刷新接口，微信侧只应收到 1 次真实刷新请求"），不能只写"实现刷新逻辑"这种模糊描述
【依赖前置任务】这个任务依赖哪些已完成的任务/接口
```

这样拆解的意义：**把每个任务的输入输出边界钉死，AI 的自由度被限制在"如何在约束内实现"，而不是"要不要遵守约束"**，这是防止屎山最有效的单一手段——比事后 review 便宜得多。

## 5. 提交前自查清单（AI 必须逐项确认后才能声明任务完成）

- [ ] 是否所有 import 符合第 1 节分层铁律
- [ ] 是否所有 error 都被 wrap 并携带上下文
- [ ] 是否有遗漏的错误处理分支（尤其是微信接口返回非 0 errcode 的情况）
- [ ] 是否涉及密钥/token 的内容出现在日志或返回体里
- [ ] 是否涉及 tenant 数据访问的地方都走了强制 tenantID 的 repository 方法
- [ ] 是否涉及并发场景（token 刷新、回调处理）的地方有对应的并发测试
- [ ] 是否有对应的单元测试，且测试真正覆盖了本次改动的分支（不是摆设）
- [ ] 是否新增/修改了数据库 schema 但没有配套迁移文件
- [ ] 单个函数/文件是否超出第 3 节的行数信号线，若超出是否有合理拆分
- [ ] 本次改动范围是否超出任务描述里"允许修改的文件范围"

任何一项未通过，不允许提交，需要先自行修正或在结果中明确标注"以下几项未满足，原因是……"交由人工确认。

## 6. Git / PR 规范

- commit message 格式：`<type>(<scope>): <subject>`，`type` 取 `feat|fix|refactor|test|chore|docs`，`scope` 对应模块名（如 `authorizer`、`token`、`callback`）
- 每个 PR 只做一件事，标题即任务名，描述里必须包含"验收标准是否达成"的说明
- 涉及安全相关改动（加解密、token 处理、回调验签）的 PR，必须在描述里显式说明"这次改动如何保证不泄露密钥/不引入新的越权路径"

---

## 7. 验收维度参考（可用于 completion-auditor 类型的审核环节）

如果由另一个 AI（审核型 subagent）来验收本规范执行情况，建议审核维度覆盖：

1. **架构符合性**：分层铁律是否违反（可通过 import 静态扫描辅助判断）
2. **契约符合性**：实现是否与任务描述里的输入输出契约一致
3. **安全符合性**：第 2 节第 7 条（密钥不落日志）、第 3.4 节信封加密是否落实
4. **测试充分性**：测试是否覆盖了任务验收标准里列出的具体场景，而不是只有一个"happy path"测试
5. **范围符合性**：改动文件是否超出任务描述允许的范围

这五个维度可以直接作为审核 rubric 的打分项，每项给出 pass/fail 及具体证据（哪一行代码、哪一个 import），而不是笼统的"看起来还行"。
