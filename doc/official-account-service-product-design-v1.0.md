# Official Account Service（微信公众号服务）产品设计文档 V1.0

## 定位

作为 OpenClaw AI 平台的一个独立微服务，为 AI Agent 提供微信公众号授权与文章发布能力，不负责运营分析、粉丝管理等复杂功能。

## 1. 产品目标

目标：

- 用户授权微信公众号给平台
- AI 或用户创建并发布公众号文章
- 平台统一管理授权账号
- 为 AI 提供统一接口

## 2. MVP 范围

包含：

- 公众号授权
- 账号管理
- 文章管理
- 文章发布
- 素材上传（图片/封面）
- 后台管理

不包含：

- 菜单
- 自定义回复
- 粉丝管理
- 数据分析
- 模板消息
- 视频号

## 3. 技术方案（Golang）

在往下写系统流程和功能模块之前，先把技术方案定下来——原因是这个服务虽然产品范围收窄了（只做授权+发布），但底层机制（token 体系、回调处理、安全设计）和更大范围的第三方平台系统是同一套东西，技术方案要先确定，后面的流程设计才有地基，也避免后续被业务需求牵着走、逐渐堆成屎山。

### 3.1 技术栈选型

选型原则和此前的技术方案保持一致：优先选生态成熟、行为可预测的库，减少 AI 编码时的幻觉式调用。

| 领域 | 选型 | 理由 |
|---|---|---|
| Web 框架 | **Gin** | 生态成熟、语料多，AI 出错率低 |
| ORM | **ent**（而非 GORM） | schema-as-code，字段/关系/索引编译期可检查 |
| 依赖注入 | **wire** | 编译期生成，出错在编译期暴露 |
| 配置管理 | **viper** + 环境变量 | 标配 |
| 日志 | **zap**（结构化） | 配合日志脱敏，见 3.4.5 |
| 缓存 / 分布式锁 | **Redis** + `redsync`（或 `singleflight`） | token 刷新并发保护 |
| 异步任务 / 重试 | **asynq**（基于 Redis） | 发布任务的异步跟踪、回调处理、重试 |
| 定时任务 | **asynq periodic task** 或 `robfig/cron` | token 主动续期、发布状态兜底轮询 |
| 加密 | 标准库 `crypto/aes`+`crypto/cipher`（GCM）+ 信封加密 | refresh_token 等敏感数据加密 |
| 数据库迁移 | **atlas**（配合 ent）或 `golang-migrate` | schema 变更可追溯、可回滚 |
| 参数校验 | `go-playground/validator` | 所有对外入参必须校验 |
| 测试 | `testify` + `mockery` | 单元测试与 mock |
| API 文档 | `swaggo` 或手写 OpenAPI | 后台管理 API 文档化 |

### 3.2 分层架构（新增 agent-api 层）

这个服务有两类调用方：AI Agent（通过第 8 节的函数式接口）和人类操作者（通过后台管理界面）。两者应该是平级的入口，都只依赖同一套 application 层，不允许互相依赖：

```
AI Agent 调用方              人类操作者（后台管理界面）
        |                            |
        v                            v
   agent-api                   interfaces/http
  (对应第8节接口)              (Dashboard/文章编辑等页面用)
        |                            |
        +-------------+  +-----------+
                      v  v
                  application
                       |
                       v
                  domain   <--  infra (实现 domain 定义的接口)
```

| 层 | 可以 import | 禁止 import |
|---|---|---|
| domain | 标准库、其他 domain 子包 | Gin、ent、Redis、asynq 等框架/基础设施包 |
| application | domain | Gin、ent 等具体实现包 |
| infra | domain（实现其接口）、具体框架 | application、agent-api、interfaces |
| agent-api | application | infra 具体实现、`interfaces/http` |
| interfaces/http | application | infra 具体实现、`agent-api` |

### 3.4 关键设计点（本产品特有，容易被忽略）

#### 3.4.1 发布是异步的，必须处理发布结果回调

微信的图文发布流程本质是"提交 → 异步处理 → 结果通知"，不是一次 HTTP 调用就能拿到最终结果：

```text
新建草稿（draft.add）
→ 提交发布（freepublish.submit，只是提交成功，不代表发布成功）
→ 微信异步处理
→ 通过回调事件通知发布结果，或主动轮询发布状态接口
→ 更新本地发布记录状态
```

**这意味着即使本产品不做"消息与自动回复"，回调接收能力仍然是必需的基础设施**——发布结果通知本身就是一种回调事件，和 2.2 节排除的"用户消息/菜单点击"是两类完全不同的东西：前者是"我们提交的操作的结果反馈"，必须处理；后者是"公众号运营互动能力"，本期不做。开发时不要把"不做消息回调"简单理解成"不需要回调接收服务"。

对应的幂等设计：发布结果通知也可能重复推送，需要按 `publish_id` 去重，处理方式与此前技术方案里"回调去重"的做法一致（复用同一套 dedup 机制）。

#### 3.4.2 两种素材接口不要混用

"上传图片"在产品里是一个动作，但背后对应微信两个完全不同的接口，返回值类型都不一样：

- **正文配图**：用"上传图文消息内的图片"接口，返回一个可直接用的图片 URL，直接嵌入文章正文 HTML 里，不占用素材库数量限制
- **封面图**：用永久素材上传接口，返回 `media_id`，发布草稿时作为 `thumb_media_id` 字段传给微信

如果 AI 编码时把这两种场景合并成一个"上传图片"函数、只处理一种返回值类型，会导致封面或正文配图其中一种功能实际不可用。`material` 领域模块内部需要按"用途"（正文配图 / 封面）区分接口调用路径，这个区分必须在 domain 层的类型设计里体现出来，而不是留给调用方"记得传对参数"。

#### 3.4.3 复用第三方平台 token 体系，不重新发明

授权、token 刷新（component_access_token / authorizer_access_token）、并发安全（singleflight + 分布式锁）、多租户隔离、密钥信封加密，这些机制和更大范围的第三方平台技术方案是同一套东西，直接复用已有设计，不因为本产品范围收窄就简化或重写一遍。具体细节见配套的技术方案文档，这里不重复展开。

#### 3.4.4 agent-api 契约设计

第 8 节的五个函数（`wechat.authorize()` 等）是 AI Agent 依赖的外部契约。设计时每个函数对应 application 层一个明确的用例（use case），agent-api 层只做参数校验和序列化，不包含业务逻辑。契约一旦发布，字段增删/含义变更需要按破坏性变更处理（详见配套的 AI 协作开发约束规范）。

#### 3.4.5 安全设计要点

- `authorizer_refresh_token`、`component_appsecret` 走信封加密（DEK/KEK 分离），密钥不进代码库
- 日志脱敏：`*secret*`、`*token*`、`*refresh*` 字段禁止原样打印
- 发布回调的解密后原始内容可以落库用于审计排查，但不能整段打进应用日志，且要有留存期限（涉及文章内容，非无限期保留）
- 所有账号数据按归属（用户/租户）隔离，repository 层强制传入归属参数，不允许裸查询绕过

## 4. 系统流程

用户登录平台 → 授权公众号 → 后台保存授权 → AI 创建文章 → 上传图片 → 提交发布 → 平台异步跟踪发布状态（回调或轮询，见 3.4.1）→ 返回最终发布结果。

## 5. 功能模块

### A. 公众号管理

- 授权公众号
- 查看公众号
- 查看授权状态
- 重新授权
- 取消授权

### B. 文章管理

- 新建文章
- 编辑文章
- 保存草稿（平台）
- 发布文章
- 查看发布状态（异步更新，见 3.4.1）

### C. 素材管理

- 上传图片（正文配图，见 3.4.2）
- 上传封面（永久素材，见 3.4.2）

### D. 后台管理

- 授权账号列表
- 发布记录
- 服务日志
- Token 状态

## 6. 页面规划

1. Dashboard：首页统计
2. 公众号管理：授权、查看状态
3. 文章列表：搜索、新建、编辑、发布
4. 编辑文章：标题、摘要、封面、正文
5. 发布记录：成功/失败状态
6. 系统管理：日志、服务状态

## 7. 页面说明

授权数量、发布数量、快捷入口。

### 公众号管理

展示名称、头像、授权状态、最后同步时间。

### 文章编辑

标题、作者、摘要、封面、正文、保存、发布。

### 发布记录

发布时间、公众号、状态、失败原因。

## 9. 开发计划

- 第一周：工程脚手架（3.2/3.3 分层结构、CI）、登录、公众号授权、后台账号管理

- 第三周：发布流程、发布结果回调处理（见 3.4.1）、发布记录
- 第四周：异常处理、测试、上线
